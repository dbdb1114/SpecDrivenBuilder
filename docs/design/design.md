# 설계 — 빌더 그래프의 큰 그림

> 결정 (2026-11-12): 노드 구성, 노드 사이를 오가는 데이터, 사용자와 주고받는 형식을 인터페이스 수준에서 정했다.
> 이 문서는 **인터페이스만** 다룬다. State 키 이름·상한 숫자·파일 구성 같은 구현 세부는 각 작업의 `plan.md` 에서 정한다.
> 질문·답의 JSON 규격은 `question-format.md`, 프로필 수집 축은 `interview-profile.md`, 구현 순서와 작업 단위는 `work-units.md`.

## 왜

비개발자는 스펙이 얼마나 상세해야 하는지 모른다. 그래서 스펙을 사용자에게 통째로 맡기지 않는다.

- 빌더는 **사용자만 아는 것**만 묻는다 (누가 쓰는가, 무엇을 넣고 무엇을 받는가, 업무 규칙과 예외, 잘 됐다고 볼 기준, 원하는 색감과 배치).
- 나머지는 작업자가 정해도 된다고 판단되는 시점에 질문을 멈춘다.
- 묻지 않은 것도 "작업자가 정함"과 기본 방향으로 스펙에 적는다. 그래야 작업자가 사용자에게 되묻지 않는다 (루트 `AGENTS.md` "품질 판정" 의 인수 조건).

## 그래프

```
요청 ─▶ interview_profile ─▶ interview_user ─▶ interview_design ─▶ select_stack ─▶ verify_stack ─▶ select_skills ─▶ confirm_spec ─▶ generate_artifacts
        (저장돼 있으면 건너뜀)      ▲           (화면 있을 때만)        │  ▲            │                            │
                                  │                                  │  └─ 버전이 ───┘                            │
                                  ├───── 부족한 정보가 있으면 ─────────┘     맞지 않으면                            │
                                  └───── 사용자가 고칠 항목을 고르면 ───────────────────────────────────────────────┘
```

| 노드 | 사용자에게 묻는가 | 입력 | 출력 |
|---|---|---|---|
| `interview_profile` | 묻는다. 저장된 프로필이 있으면 건너뛴다 | — | 프로필 |
| `interview_user` | 묻는다 | 요청 원문, 프로필, 현재 스펙 항목 | 용도·기능 스펙 항목 |
| `interview_design` | 화면이 있는 프로그램일 때만 묻는다 | 요청 원문, 현재 스펙 항목 | 디자인 스펙 항목 |
| `select_stack` | 묻지 않는다 | 스펙 항목 전체, 프로필의 환경 | 기술 스펙 항목, 또는 부족한 정보 목록 |
| `verify_stack` | 묻지 않는다 | 기술 스펙 항목 | 검증된 기술 스펙 항목, 또는 맞지 않는 항목 목록 |
| `select_skills` | 묻지 않는다 | 스펙 항목 전체, 공통 스킬 목록 | 스킬 목록 |
| `confirm_spec` | 요약을 보여 주고 확인받는다 | 스펙 항목 전체 | 확인, 또는 고칠 항목 목록 |
| `generate_artifacts` | 묻지 않는다 | 요청 원문, 프로필, 스펙 항목 전체, 스킬 목록 | 산출물 |

묻는 노드 셋(`interview_*`)은 같은 질문 묶음·답 제출 규격(`question-format.md`)을 쓴다. 프론트엔드는 화면 하나로 세 노드를 처리한다.
`confirm_spec` 의 확인 화면 규격도 `question-format.md` 에 있다.

**묻는 노드의 실행 규칙:** `interview_user` 와 `interview_design` 은 자기 영역에 결정 주체가 사용자이고 상태가 "아직 모름"인
스펙 항목이 있을 때만 묻고, 없으면 지나간다. 뒤 노드에서 돌아오는 경로는 모두 이 규칙 하나로 처리한다 —
돌아오게 하는 쪽은 항목을 "아직 모름"으로 만들기만 한다.

## 스펙 항목

노드 사이를 오가는 데이터. 스펙을 이루는 결정 하나가 스펙 항목 하나다.
고정 목록이 아니다 — LLM 이 요청을 보고 그 프로그램에 필요한 항목을 뽑는다.

| 필드 | 값 |
|---|---|
| 이름 | 무엇에 대한 결정인가 (예: "누가 쓰는가") |
| 영역 | 용도·기능 / 디자인 / 기술 |
| 결정 주체 | 사용자 (사용자만 아는 것) / 작업자 (작업자가 정해도 되는 것) |
| 상태 | 확정 / 작업자에게 맡김 / 아직 모름 |
| 내용 | 확정된 답, 또는 작업자가 따를 기본 방향 |

## 노드별 계약

### interview_profile

- 수집 축은 `interview-profile.md` 를 따른다.
- 요금은 프로그램이 아니라 사용자에 대한 정보이므로 프로필의 "환경" 축에서 묻는다.
  토큰을 직접 묻지 않는다. 쓰는 도구(Claude Code / Codex)와 요금제만 묻고, 빌더가 작업자 컨텍스트의 지침으로 번역한다.

### interview_user

- 용도(검색에 잘 걸려야 하는가, 혼자 쓰는가, 업무용인가)를 가장 먼저 묻는다. 뒤의 모든 결정이 여기에 달려 있다.
- 한 번의 LLM 호출로 스펙 항목을 갱신하고 다음 질문 묶음을 만든다.
- 질문 묶음에는 **서로 독립인 질문만** 넣는다. 앞 질문의 답에 따라 달라지는 질문은 다음 묶음으로 넘긴다.
- **종료 규칙:** 결정 주체가 사용자인 항목 중 "아직 모름"이 없으면 끝난다. 판정은 LLM 의 "충분함" 신호가 아니라
  항목 상태를 보고 코드가 한다 — 왜 멈췄는지 추적할 수 있고 fake LLM 테스트로 고정할 수 있다.
- 종료 사유는 셋이다: 판정 / 사용자가 "그만 묻고 만들어 주세요" / 안전 상한. 실행 기록에 남긴다.
- 안전 상한 (2026-11-12 결정, 작업 단위 A): 노드 진입 1회당 질문 묶음 5개. 나갈 때 다시 센다 — 돌아오는 경로로 들어오면 새로 물을 수 있어야 한다.

### interview_design

- 화면이 없는 프로그램이면 통째로 건너뛴다. 뒤 노드에서 돌아왔을 때는 "아직 모름"인 디자인 항목이 있을 때만 다시 묻는다.
- 색 톤, 레이아웃처럼 글자만으로 고르기 어려운 것을 묻는다. 선택지에 색 견본·레이아웃 그림을 붙인다 (`question-format.md` 의 `visual`).
- 답을 받으면 다음 질문 묶음에 미리보기를 실어 보내고 "이 느낌이 맞나요?"를 묻는다 (`question-format.md` 의 `preview`).
- 미리보기는 프론트엔드가 미리 만들어 둔 레이아웃 틀에 색과 문구를 입혀 그린다. LLM 이 화면 코드를 만들지 않는다 —
  LLM 호출이 늘지 않고, 결과가 깨지지 않고, LLM 이 만든 코드를 브라우저에서 실행하지 않는다.

### select_stack

- 사용자는 기술 스택을 판단할 수 없으므로 묻지 않고 정한다. 근거는 사용자의 답이다 (예: "검색에 잘 걸려야 해서").
- **버전까지 정한다** (2026-11-12 결정). 무엇을 쓰는지(예: Next.js 만 / Spring Boot + Thymeleaf)와 각각의 버전.
  방향만 정하면 스킬·AGENTS.md 에 실행 방법을 구체적으로 적을 수 없다.
- 출력은 둘 중 하나다.
  - 기술 스펙 항목 — 결정 주체는 작업자, 내용에 선택과 이유.
  - 부족한 정보 목록 — 결정 주체가 사용자이고 상태가 "아직 모름"인 스펙 항목을 추가하고 `interview_user` 로 돌아간다.
- 돌아갈 때 질문 문장을 쓰지 않는다. 무엇을 모르는지만 넘기고, 질문은 `interview_user` 가 사용자의 말로 쓴다
  ("데이터베이스가 필요한가"가 아니라 "여러 사람이 동시에 쓰나요?").
- 돌아가는 횟수에는 상한을 둔다. 상한에 닿으면 기본값으로 정하고 이유를 적는다.

### verify_stack

- 있는 이유: LLM 이 고른 버전은 학습 시점에 묶여 있어 오래됐거나, 없는 버전이거나, 서로 맞지 않을 때가 있다.
- LLM 의 기억이 아니라 **패키지 저장소의 실제 정보**로 확인한다 (npm, Maven Central, PyPI 등).
  확인할 것: 그 버전이 존재하는가, 안정판인가, 지원이 끝나지 않았는가, 함께 쓰는 것끼리 맞는가 (예: Spring Boot 버전과 Java 버전).
- 출력은 둘 중 하나다.
  - 검증된 기술 스펙 항목 — 내용에 확인한 버전과 확인 날짜를 적는다.
  - 맞지 않는 항목 목록 — 저장소에서 가져온 실제 버전 정보와 함께 `select_stack` 으로 돌아간다.
- 돌아가는 횟수에는 상한을 둔다. 상한에 닿으면 저장소의 최신 안정판으로 정하고 이유를 적는다.
- 저장소에 접속하지 못하면 검증하지 못했다는 사실을 스펙 항목에 적는다. 검증한 것처럼 넘기지 않는다.

### select_skills

- 스킬 출처는 **섞기**다: 어느 프로그램에나 쓰이는 스킬은 공통 스킬 목록에서 고르고, 그 프로그램에만 필요한 스킬은 새로 쓴다.
- 공통 스킬 목록에는 Claude Code 와 Codex 양쪽에서 실행 검증한 것만 올린다.
- 출력은 스킬 목록이다.

| 필드 | 값 |
|---|---|
| 이름 | 스킬 이름 |
| 언제 쓰는지 | 스킬 `description` 에 들어갈 내용 |
| 출처 | 공통 스킬 / 새로 씀 |
| 근거 | 이 스킬이 필요한 이유가 된 스펙 항목 |

- 미결정 전제("프로세스 가이드 방식" vs "템플릿 방식")와의 관계: 공통 스킬이 템플릿 방식 쪽, 새로 쓰는 스킬이
  프로세스 가이드 방식 쪽이다. 한쪽으로 굳히지 않으며, 비중은 품질 회귀 결과를 보고 조절한다.

### confirm_spec

- 있는 이유 (2026-11-12 결정): 빌더가 답을 잘못 이해한 채로 산출물을 만들면 사용자는 산출물을 열어 보기 전에는 알 수 없다.
- 스펙 항목을 요약해 보여 준다. 결정 주체가 사용자인 항목(확정한 것, 작업자에게 맡긴 것)은 고칠 수 있다.
  기술 항목은 선택과 이유를 한 줄로 보여 주기만 한다 — 사용자는 기술을 판단할 수 없다.
- 출력은 둘 중 하나다.
  - 확인 — `generate_artifacts` 로 간다.
  - 고칠 항목 목록 — 그 항목들을 "아직 모름"으로 바꾸고 `interview_user` 로 돌아간다. 다시 묻는 것은 묻는 노드가
    질문 묶음으로 한다. 답이 바뀌면 기술 스택이 달라질 수 있으므로 `select_stack` 부터 다시 지나온다.
- LLM 을 호출하지 않는다.

### generate_artifacts

- 스펙에 "사용자가 정한 것"과 "작업자가 정하는 것(기본 방향 포함)"을 구분해 넣는다.
  작업자는 뒤쪽 항목을 사용자에게 되묻지 않는다.
- 공통 스킬은 목록의 것을 그대로 넣고, 새로 쓰는 스킬은 스킬 목록의 이름과 "언제 쓰는지"를 받아 본문을 쓴다.
- 산출물의 "질문 규칙"(작업자가 사용자에게 한 번에 1개)은 그대로 둔다. 질문 묶음은 빌더 화면에만 적용한다 —
  빌더는 폼으로 보여 주지만 작업자는 채팅으로 묻는다.

## LLM 호출 수

| 노드 | 호출 |
|---|---|
| `interview_profile` | 실행하면 1회 이상, 건너뛰면 0회 |
| `interview_user` | 질문 묶음 하나당 1회 |
| `interview_design` | 실행하면 질문 묶음 하나당 1회 |
| `select_stack` | 1회, 돌아갈 때마다 1회 추가 |
| `verify_stack` | 저장소 조회는 LLM 호출이 아니다. 함께 쓰는 것끼리 맞는지를 LLM 으로 판정하면 1회 (미결정) |
| `select_skills` | 1회 |
| `confirm_spec` | 0회. 사용자가 고치면 돌아간 경로의 노드들이 다시 호출된다 |
| `generate_artifacts` | 1회 |

질문을 하나씩 묻던 구조보다 `interview_user` 의 호출은 줄고, 노드가 늘어난 만큼 고정 호출이 늘어난다.
노드를 나눈 이유: 디자인은 건너뛸 수 있어야 하고 프롬프트가 한 주제에 집중해야 질문 품질이 나온다.
기술 스택과 스킬은 빌더가 정해야 스킬·AGENTS.md 에 실행 방법을 구체적으로 적을 수 있다.

## 현재 구현과의 차이 (2026-11-12 기준)

- 구현된 노드는 `interview_user`, `generate_artifacts` 둘뿐이다.
- `interview_user` 는 질문을 하나씩 묻고, 문답 기록만 넘기며, 질문 3개 상한에서 끝난다. 스펙 항목이 없다.
- 질문은 문자열 하나다. JSON 규격이 없다.
- FastAPI · 프론트엔드는 아직 없다.

## 미결정

- `verify_stack` 의 확인 방법 — 지원할 패키지 저장소 목록, "함께 쓰는 것끼리 맞는가"를 저장소 정보만으로 판정할지 LLM 을 쓸지.
- `select_stack` 이 버전을 정하는 범위 — 주요 도구만인지, 세부 라이브러리까지인지.
- 공통 스킬 목록에 처음 넣을 스킬.
- `select_stack` → `interview_user`, `verify_stack` → `select_stack` 으로 돌아가는 횟수 상한.
- 프로필 저장 위치 (`interview-profile.md` "열린 질문").
