# 설계 — 빌더 그래프의 큰 그림

> 결정 (2026-11-12): 노드 구성, 노드 사이를 오가는 데이터, 사용자와 주고받는 형식을 인터페이스 수준에서 정했다.
> 이 문서는 **인터페이스만** 다룬다. State 키 이름·상한 숫자·파일 구성 같은 구현 세부는 각 작업의 `plan.md` 에서 정한다.
> 질문·답의 JSON 규격은 `question-format.md`, 프로필 수집 축은 `interview-profile.md`, 구현 순서와 작업 단위는 `work-units.md`.

## 왜

비개발자는 스펙이 얼마나 상세해야 하는지 모른다. 그래서 스펙을 사용자에게 통째로 맡기지 않는다.

- 빌더는 **사용자만 아는 것**만 묻는다 (누가 쓰는가, 무엇을 넣고 무엇을 받는가, 업무 규칙과 예외, 잘 됐다고 볼 기준, 원하는 색감과 배치).
- 나머지는 작업자가 정해도 된다고 판단되는 시점에 질문을 멈춘다.
- 묻지 않은 것도 "작업자가 정함"과 기본 방향으로 스펙에 적는다. 그래야 작업자가 사용자에게 되묻지 않는다 (루트 `AGENTS.md` "품질 판정" 의 인수 조건).

## 그래프

```
요청 ─▶ interview_profile ─▶ interview_user ─▶ interview_design ─▶ select_stack ─▶ verify_stack ─▶ select_skills ─▶ confirm_spec ─▶ generate_artifacts
        (저장돼 있으면 건너뜀)      ▲           (화면 있을 때만)        │  ▲            │                            │
                                  │                                  │  └─ 버전이 ───┘                            │
                                  ├───── 부족한 정보가 있으면 ─────────┘     맞지 않으면                            │
                                  └───── 사용자가 고칠 항목을 고르면 ───────────────────────────────────────────────┘
```

| 노드 | 사용자에게 묻는가 | 입력 | 출력 |
|---|---|---|---|
| `interview_profile` | 묻는다. 저장된 프로필이 있으면 건너뛴다 | — | 프로필 |
| `interview_user` | 묻는다 | 요청 원문, 프로필, 현재 스펙 항목 | 용도·기능 스펙 항목 |
| `interview_design` | 화면이 있는 프로그램일 때만 묻는다 | 요청 원문, 현재 스펙 항목 | 디자인 스펙 항목 |
| `select_stack` | 묻지 않는다 | 스펙 항목 전체, 프로필의 환경 | 기술 스펙 항목, 또는 부족한 정보 목록 |
| `verify_stack` | 묻지 않는다 | 기술 스펙 항목 | 검증된 기술 스펙 항목, 또는 맞지 않는 항목 목록 |
| `select_skills` | 묻지 않는다 | 스펙 항목 전체, 공통 스킬 목록 | 스킬 목록 |
| `confirm_spec` | 요약을 보여 주고 확인받는다 | 스펙 항목 전체 | 확인, 또는 고칠 항목 목록 |
| `generate_artifacts` | 묻지 않는다 | 요청 원문, 프로필, 스펙 항목 전체, 스킬 목록 | 산출물 |

묻는 노드 셋(`interview_*`)은 같은 질문 묶음·답 제출 규격(`question-format.md`)을 쓴다. 프론트엔드는 화면 하나로 세 노드를 처리한다.
`confirm_spec` 의 확인 화면 규격도 `question-format.md` 에 있다.

**묻는 노드의 실행 규칙:** `interview_user` 와 `interview_design` 은 자기 영역에 결정 주체가 사용자이고 상태가 "아직 모름"인
스펙 항목이 있을 때만 묻고, 없으면 지나간다. 뒤 노드에서 돌아오는 경로는 모두 이 규칙 하나로 처리한다 —
돌아오게 하는 쪽은 항목을 "아직 모름"으로 만들기만 한다.

## 스펙 항목

노드 사이를 오가는 데이터. 스펙을 이루는 결정 하나가 스펙 항목 하나다.
고정 목록이 아니다 — LLM 이 요청을 보고 그 프로그램에 필요한 항목을 뽑는다.

| 필드 | 값 |
|---|---|
| 이름 | 무엇에 대한 결정인가 (예: "누가 쓰는가") |
| 영역 | 용도·기능 / 디자인 / 기술 |
| 결정 주체 | 사용자 (사용자만 아는 것) / 작업자 (작업자가 정해도 되는 것) |
| 상태 | 확정 / 작업자에게 맡김 / 아직 모름 |
| 내용 | 확정된 답, 또는 작업자가 따를 기본 방향 |

## 공통 항목

> 결정 (2026-11-14). 구현 (2026-11-14, 작업 단위 H) — 목록 원본은 `builder/prompts/common_items.json`, 읽기·질문 붙이기는 `specbuilder/common_items.py`.

유효성 검증, 글자 크게/작게 보기처럼 여러 프로그램에 되풀이되는 결정은 LLM 이 매번 새로 뽑지 않고 **공통 항목**으로 미리 써 둔다.
LLM 에게 맡기면 프로그램마다 묻기도 하고 빠뜨리기도 하고, 질문 문구와 선택지가 흔들린다.

| 필드 | 값 |
|---|---|
| id · 이름 · 영역 | 스펙 항목과 같다. id 는 고정이다 |
| 언제 넣는가 | 이 항목이 필요한 프로그램의 조건 (예: "사용자가 값을 직접 입력하는 곳이 있다") |
| 결정 주체 | 사용자 — 고정 질문으로 묻는다 / 작업자 — 묻지 않고 기본 방향을 그대로 넣는다 |
| 질문 문구 · 선택지 | 결정 주체가 사용자일 때. 개발 용어 없이 쓴다 ("유효성 검증"이 아니라 "잘못 입력했을 때 어떻게 알려 줄까요?") |
| 기본 방향 | 결정 주체가 작업자이거나 사용자가 "알아서 정해 주세요"를 골랐을 때 항목 내용이 된다 |

- **노드를 추가하지 않는다.** 공통 항목은 영역을 갖고, 그 영역의 묻는 노드가 다룬다 — 용도·기능은 `interview_user`,
  디자인은 `interview_design`. 접근성만 묻는 노드를 따로 두면 LLM 호출과 질문 단계가 하나씩 늘지만 하는 일은 묻는 노드와 같다.
- **넣을지는 LLM 이, 무엇을 물을지는 코드가 정한다.** 묻는 노드의 LLM 은 공통 항목 목록(id · 언제 넣는가)을 입력으로 받아
  이 프로그램에 해당하는 것의 id 만 고른다. 질문 문구·선택지·기본 방향은 빌더 코드가 목록에서 가져와 붙인다.
  LLM 이 공통 항목의 질문을 직접 쓰면 그 응답은 버린다. LLM 호출 수는 늘지 않는다.
- 공통 항목도 스펙 항목이다. 질문 묶음·답 제출·확인 화면·산출물은 다른 항목과 똑같이 지나간다.
- 구현 (2026-11-14, 작업 단위 H): LLM 응답에 `common_items`(id 목록)를 더한다. 고정 질문은 그 묶음의 LLM 질문 뒤에 붙고,
  묶음 상한(10개)을 넘으면 다음 묶음으로 미룬다. 선택지마다 사용자에게 보이는 말과 따로 **항목 내용이 될 작업자용 문장**을 두어,
  답이 라벨("네, 넣어 주세요")만 남아 뜻이 흐려지지 않게 한다. 맡김·그만 묻기·상한이면 코드가 기본 방향을 바로 넣는다.
  문구·선택지는 `docs/work/261114-common-items/plan.md` "Q2".
- 첫 목록:

| id | 영역 | 언제 넣는가 | 결정 주체 |
|---|---|---|---|
| `input-validation` | 용도·기능 | 사용자가 값을 직접 입력하는 곳이 있다 | 사용자 — 잘못 입력했을 때 알려 주는 방식 |
| `text-size` | 디자인 | 화면이 있다 | 사용자 — 글자 크게/작게 보기를 넣을지 |
| `basic-accessibility` | 디자인 | 화면이 있다 | 작업자 — 글자와 바탕의 대비, 키보드만으로 쓰기, 그림의 설명 글 |

- 미결정 전제("프로세스 가이드 방식" vs "템플릿 방식")와의 관계: 공통 스킬과 같다. 공통 항목이 템플릿 방식 쪽,
  LLM 이 뽑는 항목이 프로세스 가이드 방식 쪽이며 한쪽으로 굳히지 않는다.

## 노드별 계약

### interview_profile

- 수집 축은 `interview-profile.md` 를 따른다.
- 요금은 프로그램이 아니라 사용자에 대한 정보이므로 프로필의 "환경" 축에서 묻는다.
  토큰을 직접 묻지 않는다. 쓰는 도구(Claude Code / Codex)와 요금제만 묻고, 빌더가 작업자 컨텍스트의 지침으로 번역한다.
- 결정 (2026-11-14, 작업 단위 G): 고정 질문 묶음 1개(6문항), LLM 호출 0회. 저장은 `~/.specbuilder/profile.json`
  (`SPECBUILDER_PROFILE_PATH`). 결정 위임 범위는 `interview_user` 에, 환경은 `select_stack` 에, 다섯 축 전부는 `generate_artifacts` 에 들어간다.
  상세와 이유는 `interview-profile.md` "결정". 갱신 흐름은 다음 작업으로 미룸.

### interview_user

- 용도(검색에 잘 걸려야 하는가, 혼자 쓰는가, 업무용인가)를 가장 먼저 묻는다. 뒤의 모든 결정이 여기에 달려 있다.
- 한 번의 LLM 호출로 스펙 항목을 갱신하고 다음 질문 묶음을 만든다.
- 질문 묶음에는 **서로 독립인 질문만** 넣는다. 앞 질문의 답에 따라 달라지는 질문은 다음 묶음으로 넘긴다.
- **종료 규칙:** 결정 주체가 사용자인 항목 중 "아직 모름"이 없으면 끝난다. 판정은 LLM 의 "충분함" 신호가 아니라
  항목 상태를 보고 코드가 한다 — 왜 멈췄는지 추적할 수 있고 fake LLM 테스트로 고정할 수 있다.
- 종료 사유는 셋이다: 판정 / 사용자가 "그만 묻고 만들어 주세요" / 안전 상한. 실행 기록에 남긴다.
- 안전 상한 (2026-11-12 결정, 작업 단위 A): 노드 진입 1회당 질문 묶음 5개. 나갈 때 다시 센다 — 돌아오는 경로로 들어오면 새로 물을 수 있어야 한다.
- 용도·기능 영역의 공통 항목을 다룬다 — 위 "공통 항목" (2026-11-14 구현, 작업 단위 H).

### interview_design

- 화면이 없는 프로그램이면 통째로 건너뛴다. 뒤 노드에서 돌아왔을 때는 "아직 모름"인 디자인 항목이 있을 때만 다시 묻는다.
- 색 톤, 레이아웃처럼 글자만으로 고르기 어려운 것을 묻는다. 선택지에 색 견본·레이아웃 그림을 붙인다 (`question-format.md` 의 `visual`).
- 답을 받으면 다음 질문 묶음에 미리보기를 실어 보내고 "이 느낌이 맞나요?"를 묻는다 (`question-format.md` 의 `preview`).
- 미리보기는 프론트엔드가 미리 만들어 둔 레이아웃 틀에 색과 문구를 입혀 그린다. LLM 이 화면 코드를 만들지 않는다 —
  LLM 호출이 늘지 않고, 결과가 깨지지 않고, LLM 이 만든 코드를 브라우저에서 실행하지 않는다.
- 구현 (2026-11-14, 작업 단위 F): 첫 진입에 LLM 이 화면 유무를 판정한다. 화면이 없으면 `screen` 항목(작업자에게 맡김)을 남기고 지나가며,
  돌아오는 경로에서는 다시 판정하지 않는다. 색 톤·배치 항목 id 는 `color-tone`·`layout` 으로 고정하고, 고른 색 값·배치 key 를
  항목 내용에 함께 적는다 (작업자가 그대로 쓴다). 미리보기 답은 `preview-check` 항목이 받고, "색을/배치를 바꿀래요"는 그 항목만 "아직 모름"으로 되돌린다.
- 디자인 영역의 공통 항목을 다룬다 — 위 "공통 항목" (2026-11-14 구현, 작업 단위 H). 화면이 없으면 판정 그대로 지나가므로 고르지 않는다.
- (2026-11-14 결정, 구현 전 — 작업 단위 I) 미리보기를 실제 화면처럼 그린다. 우리가 정하는 것은 배치와 색뿐이므로 규격은
  그 둘만 넓힌다: 색에 역할 이름을 붙이고, 틀을 채울 문구를 늘린다 (`question-format.md` 의 `preview`).
  LLM 이 화면 코드를 만들지 않는 원칙은 그대로다.

### select_stack

- 사용자는 기술 스택을 판단할 수 없으므로 묻지 않고 정한다. 근거는 사용자의 답이다 (예: "검색에 잘 걸려야 해서").
- **버전까지 정한다** (2026-11-12 결정). 무엇을 쓰는지(예: Next.js 만 / Spring Boot + Thymeleaf)와 각각의 버전.
  방향만 정하면 스킬·AGENTS.md 에 실행 방법을 구체적으로 적을 수 없다.
- 출력은 둘 중 하나다.
  - 기술 스펙 항목 — 결정 주체는 작업자, 내용에 선택과 이유.
  - 부족한 정보 목록 — 결정 주체가 사용자이고 상태가 "아직 모름"인 스펙 항목을 추가하고 `interview_user` 로 돌아간다.
- 돌아갈 때 질문 문장을 쓰지 않는다. 무엇을 모르는지만 넘기고, 질문은 `interview_user` 가 사용자의 말로 쓴다
  ("데이터베이스가 필요한가"가 아니라 "여러 사람이 동시에 쓰나요?").
- 돌아가는 횟수에는 상한을 둔다. 상한에 닿으면 기본값으로 정하고 이유를 적는다.
- 결정 (2026-11-13, 작업 단위 B):
  - 버전을 정하는 범위는 **주요 도구만** — 런타임, 프레임워크, 데이터베이스, 설치·실행 명령에 이름이 나오는 핵심 라이브러리.
    항목당 4개, 전체 10개 이하. 세부 라이브러리는 작업자가 정한다.
  - `interview_user` 로 돌아가는 횟수 상한은 **실행 전체에서 1회**. `interview_user` 는 한 번 들어가면 묶음 5개까지 물을 수 있다.
  - 기술 항목은 결정 주체 작업자 · 상태 맡김. 다시 정할 때는 통째로 교체한다. 버전은 content 의
    `버전: (npm: next@16.4.6), (eol: nodejs@24)` 줄에 적고 `verify_stack` 이 이 줄을 읽는다 (`registry/refs.py`).

### verify_stack

- 있는 이유: LLM 이 고른 버전은 학습 시점에 묶여 있어 오래됐거나, 없는 버전이거나, 서로 맞지 않을 때가 있다.
- LLM 의 기억이 아니라 **패키지 저장소의 실제 정보**로 확인한다 (npm, Maven Central, PyPI 등).
  확인할 것: 그 버전이 존재하는가, 안정판인가, 지원이 끝나지 않았는가, 함께 쓰는 것끼리 맞는가 (예: Spring Boot 버전과 Java 버전).
- 출력은 둘 중 하나다.
  - 검증된 기술 스펙 항목 — 내용에 확인한 버전과 확인 날짜를 적는다.
  - 맞지 않는 항목 목록 — 저장소에서 가져온 실제 버전 정보와 함께 `select_stack` 으로 돌아간다.
- 돌아가는 횟수에는 상한을 둔다. 상한에 닿으면 저장소의 최신 안정판으로 정하고 이유를 적는다.
- 저장소에 접속하지 못하면 검증하지 못했다는 사실을 스펙 항목에 적는다. 검증한 것처럼 넘기지 않는다.
- 결정 (2026-11-13, 작업 단위 B):
  - 저장소: **npm · PyPI · Maven Central**, 지원 종료는 **endoflife.date** (패키지 저장소에 지원 종료 정보가 없어서).
  - 호환 판정은 **저장소 정보만, LLM 없음** (LLM 호출 0회) — LLM 으로 판정하면 다시 학습 시점 기억에 기댄다.
    확인하는 조합: npm `engines.node` ↔ Node, npm `peerDependencies` ↔ 같이 고른 npm 패키지, PyPI `requires_python` ↔ Python,
    Spring Boot `supportedJavaVersions` ↔ Java. 이 밖의 조합은 "저장소에 정보 없음" 으로 적는다.
  - `select_stack` 으로 돌아가는 횟수 상한은 **2회** (`select_stack` 이 검증에서 오지 않은 새 진입이면 다시 센다).
    상한에서는 코드가 최신 안정판으로 바꾸고, 바꾼 버전으로 다시 판정해 남은 불일치는 "맞지 않음" 으로 그대로 적는다.

### select_skills

- 스킬 출처는 **섞기**다: 어느 프로그램에나 쓰이는 스킬은 공통 스킬 목록에서 고르고, 그 프로그램에만 필요한 스킬은 새로 쓴다.
- 공통 스킬 목록에는 Claude Code 와 Codex 양쪽에서 실행 검증한 것만 올린다.
  예외 (2026-11-14): 첫 공통 스킬 `verify-before-report` 는 Claude Code 에서만 실행 검증했고 Codex 검증은 대기 중이다
  (작업한 PC 에 Codex 가 없었다). 검증 기록은 `docs/work/261113-select-skills/plan.md`.
- 출력은 스킬 목록이다.

| 필드 | 값 |
|---|---|
| 이름 | 스킬 이름 |
| 언제 쓰는지 | 스킬 `description` 에 들어갈 내용 |
| 출처 | 공통 스킬 / 새로 씀 |
| 근거 | 이 스킬이 필요한 이유가 된 스펙 항목 |

- 공통 스킬 목록 (2026-11-13 결정): `builder/templates/skills/<이름>/SKILL.md` 폴더가 곧 목록이다. 이름과 "언제 쓰는지"는
  각 SKILL.md 의 frontmatter 에서 읽는다 — 목록 파일을 따로 두지 않아 목록과 본문이 어긋나지 않는다.
  첫 공통 스킬은 `verify-before-report` (마쳤다고 말하기 전에 실제로 실행해 확인하고 사용자의 말로 보고) — Codex 미검증, 위 예외.
- 스킬 수는 1~6개이고, 그 프로그램을 만드는 순서를 다루는 새로 쓰는 스킬이 반드시 하나 있다. 근거는 있는 스펙 항목만 댈 수 있다.
- 산출물에서 스킬을 두는 경로 (2026-11-13 결정): 스킬마다 `.claude/skills/<이름>/SKILL.md` 와 `.agents/skills/<이름>/SKILL.md`
  두 곳에 같은 내용을 넣는다. Claude Code 는 앞의 것만, Codex 는 뒤의 것만 발견한다 — 두 작업자가 같이 읽는 경로가 없다.
  새로 쓰는 스킬의 frontmatter 는 LLM 이 아니라 빌더 코드가 스킬 목록의 값으로 채운다.
- 미결정 전제("프로세스 가이드 방식" vs "템플릿 방식")와의 관계: 공통 스킬이 템플릿 방식 쪽, 새로 쓰는 스킬이
  프로세스 가이드 방식 쪽이다. 한쪽으로 굳히지 않으며, 비중은 품질 회귀 결과를 보고 조절한다.

### confirm_spec

- 있는 이유 (2026-11-12 결정): 빌더가 답을 잘못 이해한 채로 산출물을 만들면 사용자는 산출물을 열어 보기 전에는 알 수 없다.
- 스펙 항목을 요약해 보여 준다. 결정 주체가 사용자인 항목(확정한 것, 작업자에게 맡긴 것)은 고칠 수 있다.
  기술 항목은 선택과 이유를 한 줄로 보여 주기만 한다 — 사용자는 기술을 판단할 수 없다.
- 출력은 둘 중 하나다.
  - 확인 — `generate_artifacts` 로 간다.
  - 고칠 항목 목록 — 그 항목들을 "아직 모름"으로 바꾸고 `interview_user` 로 돌아간다. 다시 묻는 것은 묻는 노드가
    질문 묶음으로 한다. 답이 바뀌면 기술 스택이 달라질 수 있으므로 `select_stack` 부터 다시 지나온다.
- LLM 을 호출하지 않는다.
- (2026-11-13 결정) 고칠 수 있는 항목(`editable`)은 결정 주체가 사용자이고 기술 영역이 아닌 항목이다 — 기술 항목은 아직 모름으로 바꿔도 다시 묻는 노드가 없다.
- (2026-11-13 결정) 확인 화면에 "아직 모름" 항목이 있으면 앞 노드의 버그로 보고 멈춘다(규격에도 실을 수 없다). 고른 항목은 내용을 비우고 아직 모름으로 바꾼다 — 이전 답은 문답 기록에 남아 다시 물을 때 쓰인다.

### generate_artifacts

- 스펙에 "사용자가 정한 것"과 "작업자가 정하는 것(기본 방향 포함)"을 구분해 넣는다.
  작업자는 뒤쪽 항목을 사용자에게 되묻지 않는다.
- 공통 스킬은 목록의 것을 그대로 넣고, 새로 쓰는 스킬은 스킬 목록의 이름과 "언제 쓰는지"를 받아 본문을 쓴다.
- 산출물의 "질문 규칙"(작업자가 사용자에게 한 번에 1개)은 그대로 둔다. 질문 묶음은 빌더 화면에만 적용한다 —
  빌더는 폼으로 보여 주지만 작업자는 채팅으로 묻는다.
- (2026-11-14 결정, 작업 단위 J 에서 구현) **산출물의 폴더 구성.** zip 을 풀면 루트에 아래가 있다.

```
AGENTS.md  CLAUDE.md            공통 규칙 (용어사전 · 작업자 컨텍스트 · 작업 절차 · 질문 규칙 · 완료 보고 규칙 · 구조)
docs/spec.md                    스펙
frontend/AGENTS.md  CLAUDE.md   화면이 있을 때만
backend/AGENTS.md   CLAUDE.md   서버가 있을 때만
database/AGENTS.md  CLAUDE.md   데이터베이스가 있을 때만
.claude/skills/…  .agents/skills/…
```

  - `frontend/` · `backend/` · `database/` 는 **`select_stack` 이 고른 기술에 있는 것만** 넣는다. 빈 폴더나 "쓰지 않음"만 적힌 문서를
    만들지 않는다 (산출물 규칙의 플레이스홀더 금지). 스크립트 하나짜리 프로그램은 루트 문서와 `docs/` 만 받는다.
  - 어느 폴더를 넣을지는 LLM 이 쓴 글이 아니라 기술 스펙 항목을 보고 **빌더 코드가** 정한다 — 파일이 빠지거나 남지 않는다.
    그래서 `select_stack` 은 프로그램이 어떤 부분(화면 / 서버 / 데이터베이스)으로 이루어지는지를 기술 스펙 항목에 밝힌다.
  - 폴더별 `AGENTS.md` 는 섹션이 고정이다: **구조 · 명령어 · 코드 규칙 · 하지 말 것** (이 레포의 `builder/AGENTS.md` 가 레퍼런스).
    내용은 `verify_stack` 이 확인한 기술과 버전으로 채운다. 언어별 규칙은 루트 `AGENTS.md` 에 쓰지 않는다.
  - 폴더별 `CLAUDE.md` 는 `@AGENTS.md` 한 줄. Claude Code 는 그 폴더의 파일을 건드릴 때 읽는다.
    Codex 는 하위 폴더의 `AGENTS.md` 를 스스로 찾지 않고 사용자는 폴더별로 세션을 열지 않으므로,
    루트 `AGENTS.md` 의 작업 절차에 "그 폴더의 파일을 고치기 전에 그 폴더의 `AGENTS.md` 를 읽는다"를 적는다.
  - 루트 `AGENTS.md` 의 "구조" 섹션에 폴더 구조도(위에서 두 단계까지)와 폴더마다 한 줄 설명을 넣는다.
    구조가 없으면 작업자가 매번 다르게 잡고, 스킬에 "어느 폴더의 무엇을 고친다"를 적을 수 없다. 새로 쓰는 스킬은 이 구조의 경로만 가리킨다.
  - 폴더에는 문서만 들어간다. 코드는 작업자가 만든다.
  - LLM 호출은 우선 1회를 유지한다. 한 번에 쓰는 파일이 늘어 뒤쪽 파일이 부실해지면 호출을 나눌지 그때 묻는다.
  - 결정 (2026-11-14, 작업 단위 J):
    - 부분 표기: `select_stack` 이 기술 항목마다 `parts`(`frontend`·`backend`·`database`, 0개 이상)를 내고, 내용에
      `부분: 화면, 서버` 줄로 적는다 (`registry/refs.py`). 부분 = 코드가 따로 사는 폴더 — 화면과 서버를 한 프레임워크로 만들면
      화면 하나, 엑셀·CSV·JSON 파일 저장은 데이터베이스가 아니다. 런타임처럼 여러 부분이 같이 쓰는 항목은 비운다.
      폴더별 `AGENTS.md` 입력에는 그 폴더의 기술 항목과 공통 항목을 넘긴다.
    - 구조도: LLM 이 루트 `AGENTS.md` 의 `## 구조` 절에 코드블록으로, 두 단계까지 쓴다. 빌더 코드는 그 절이 있는지, `docs/` 와
      넣은 폴더가 모두 나오는지, 폴더별 `AGENTS.md` 에 고정 섹션 넷이 있는지 확인하고 아니면 실패시킨다.
    - `database/AGENTS.md` 는 표 설계·변경 기록(마이그레이션)과 데이터 안전만. 데이터를 읽고 쓰는 코드의 규칙은 그 코드의 폴더에.
    - 완료 화면에 구조도는 보여 주지 않는다 (파일 목록이 이미 있다). 완료 화면과 공통 스킬 `verify-before-report` 는 `docs/spec.md` 를 가리킨다.
